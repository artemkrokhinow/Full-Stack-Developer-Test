# ЖЕСТКИЕ ПРАВИЛА БЭКЕНДА (NODE.JS + PRISMA + EXPRESS)

## 1. БАЗА ДАННЫХ И CONCURRENCY (ЗАЩИТА ОТ ГОНОК)

- **Атомарность:** КАТЕГОРИЧЕСКИ ЗАПРЕЩЕН паттерн "read-modify-write" в памяти приложения Node.js [1]. Любые обновления счетчиков (баланс, сток) выполнять исключительно через атомарные операторы Prisma (`increment`/`decrement`) с проверкой остатка на уровне БД (`where: { stock: { gte: quantity } }`).
- **Явные блокировки:** При реализации сложных транзакций, зависящих от предварительного чтения (защита от Write Skew), ОБЯЗАТЕЛЬНО применять пессимистичную блокировку через сырой SQL: `SELECT ... FOR UPDATE` [1, 2].
- **Аудит-логи:** Любое изменение критичных данных (списание товара) обязано сопровождаться атомарной записью в лог (`InventoryLog`) строго в рамках единой `prisma.$transaction`.

## 2. ИДЕМПОТЕНТНОСТЬ API

- **Метаданные:** Все мутирующие эндпоинты (POST/PUT/PATCH/DELETE) обязаны принимать `Idempotency-Key` (UUID) из заголовка или тела запроса.
- **Ограничения СУБД:** Поле `idempotencyKey` в Prisma-схеме обязано иметь ограничение `@unique`.
- **Идемпотентный возврат:** При перехвате ошибки нарушения уникальности (код Prisma `P2002` по ключу идемпотентности) сервер НЕ ДОЛЖЕН падать. Вместо 500 ошибки необходимо выполнить поиск уже существующей записи и вернуть клиенту успешный ответ предыдущей транзакции [1, 2].

## 3. CLEAN ARCHITECTURE (РАЗДЕЛЕНИЕ СЛОЕВ)

- **Тонкие контроллеры:** HTTP-контроллеры выполняют строго три задачи: парсинг запроса, вызов Zod-валидатора и вызов метода сервиса. Вся бизнес-логика здесь запрещена.
- **Изоляция сервисов:** Слой сервисов (Business Logic) полностью изолирован от Express. ЗАПРЕЩЕНО передавать объекты `req` и `res` в сервисы. ЗАПРЕЩЕНО оперировать HTTP-статусами (400, 404) внутри бизнес-логики.
- **Доменные ошибки:** При нарушении бизнес-правил сервисы выбрасывают исключительно кастомные исключения (наследующие базовый класс `DomainError`), которые не содержат привязки к протоколу.

## 4. ОБРАБОТКА ОШИБОК И FAIL-FAST

- **Централизация:** Трансляция классов `DomainError` в соответствующие HTTP-коды выполняется строго в едином месте — глобальном Error Middleware в Express.
- **Fail-Fast механизм:** При возникновении неперехваченных системных или программных исключений (`uncaughtException`, `unhandledRejection` или ошибки, не являющиеся `DomainError`) процесс Node.js должен быть немедленно завершен `process.exit(1)` [2]. ЗАПРЕЩЕНО оставлять процесс работать с поврежденным состоянием.

## 5. OBSERVABILITY (НАБЛЮДАЕМОСТЬ)

- **Correlation ID:** Каждому входящему запросу при входе присваивается UUID, который сохраняется в контексте `AsyncLocalStorage`. Все последующие вызовы логгера обязаны автоматически извлекать и прикреплять этот ID [1, 2].
- **Структура JSON:** Логи пишутся в структурированном виде (паттерн Envelope). В объекте обязательно наличие `timestamp`, `correlationId`, `level` и вложенного блока `payload`.
- **Защита данных:** КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО логировать пароли, секреты, токены и PII (персональные данные пользователей) для предотвращения утечек.

## 6. ФОНОВЫЕ ЗАДАЧИ И WORKERS

- **Асинхронность:** Тяжелые фоновые задачи (снятие резервов, очистка кэша) ЗАПРЕЩЕНО вызывать внутри синхронного цикла обработки HTTP-запроса [2].
- **Конкурентные консьюмеры (Competing Consumers):** В кластерной среде фоновые задачи реализуются через очередь (например, BullMQ + Redis). Задача помещается в очередь и обрабатывается только одним воркером, исключая конфликты масштабирования [2].
